# Shared lessons

Shared memory of the sessions that design structures for Heraldia. Each bullet is short and says what was learned and how it was verified
(test server, 26.3 code, audit, the owner's screenshot). The starting lessons are in `docs/DEVELOPMENT.md`.

## Game behavior (26.3)

- Since 26.x there are no always-loaded spawn chunks ("Loading 0 persistent chunks"): for `/place structure` from the console you first have to `forceload` the whole box of the structure. Verified on a dedicated server.
- The dedicated server pauses after 60 s without players (`pause-when-empty-seconds`) and stops loading chunks. In tests, set it to 0. Verified on a dedicated server.
- `ServerLifecycleEvents.SERVER_STARTED` fires after the "Done" message. Verified on a dedicated server.
- The loot condition registry (`BuiltInRegistries.LOOT_CONDITION_TYPE`) stores the `MapCodec` directly, without a type wrapper. Verified when compiling.
- Villager trades are data: `villager_trade/<profession>/<level>/*.json`, the tag `#minecraft:<profession>/level_N` (entries are added with `"replace": false`) and `trade_set` (how many are drawn from the tag; the level 5 cartographer draws 2). `merchant_predicate` filters by villager. Verified in misode/mcmeta 26.3-data and by loading our own trades on a dedicated server.
- Neither the modifier nor the condition `minecraft:reference` exists: a shared `item_modifier` cannot be referenced from loot or trades, it has to be written inline. An `item_modifier` file must be an object (a list gives "Not a JSON object"). Conditions are written `{"type": ...}`, and a loot pool takes a single `"condition"` (not the `conditions` list). Verified with registry errors on a dedicated server.
- `exploration_map` works on `minecraft:filled_map`. Without a destination, `filtered` + `discard` leaves the item empty ("Dropped 0 [Air]"). With `skip_existing_chunks: false` and 8 rings (289 cells) without any valid biome, the search answers in under 0.1 s. Verified with `loot spawn` on a dedicated server.
- The entity predicate `{"nbt": "{Tags:[\"heraldia\"]}"}` still works in 26.3 (in the `predicate=` selector and as `merchant_predicate`). Verified on a dedicated server with a village villager and a vanilla one.

- `/locate` does not go through the placement's `isPlacementChunk`: it uses `getPotentialStructureChunk` and then `StructureCheck.checkStart`, which only calls `applyAdditionalChunkRestrictions` and `canCreateStructure`. A custom placement that limits cells must also filter in `applyAdditionalChunkRestrictions`, or `/locate` will point at places where nothing generates. Verified in the 26.3 code and with `/locate` in the smoke test.
- `ChunkGenerator.findNearestMapStructure` only knows how to search `concentric_rings` and `random_spread` (with `instanceof`): a custom placement type must extend `RandomSpreadStructurePlacement` for `/locate` and maps to find it. Its `codec()` has to return `MapCodec<RandomSpreadStructurePlacement>` (unchecked cast). Verified when compiling and with `/locate`.
- `BuiltInRegistries.STRUCTURE_PLACEMENT` also stores the `MapCodec` directly. Worldgen datapacks are read after `onInitialize`, so a configuration read there is already available when the placement is decoded. Verified on a dedicated server (order of the lines in the log).
- In a `structure_set` with several structures, if `tryGenerateStructure` returns false (invalid biome or a mixin that rejects it), that entry is removed and another is drawn with the same cell seed. Rejecting entries is the clean way to disable styles or fix the size. Verified in the 26.3 code.
- A chunk only looks for structure starts within ±8 chunks (`ChunkGenerator.createReferences`, `range = 8`): a piece more than 8 chunks from its start chunk is never placed, with no error. A start covers at most 17 × 17 chunks (272 blocks); anything larger needs several starts. Verified in the 26.3 code (Atlantis).
- Dry areas under water: with `liquid_settings: ignore_waterlogging` on the structure, the template's air stays dry and waterloggable blocks keep their state; with the default value (`apply_waterlogging`) waterloggable blocks placed where there was water become waterlogged and flood the room. A closed door holds the water back and a "moon pool" (water under air) does not rise. Any water you want must be in the template. Verified on a dedicated server with natural generation in a deep ocean, reading the blocks after 30 s and after 2 min (Atlantis).
- Breaking a wall block of a submerged dry room floods it in seconds (vanilla). Verified on the same server with `setblock`.
- In the console, `execute as @e[...] at @s if block ...` writes one "Test passed" line per entity: to count in an automatic test, add to a scoreboard with a unique name per check and read it with `scoreboard players get`. Verified on a dedicated server (the first version of the test read out-of-sync results).
- In generation (worldgen) there are no redstone updates: the initial states of torches, dust and doors must already be written consistently in the template; the first lever that is flipped recalculates the rest. Verified on a dedicated server with two combination doors (Atlantis).
- `setblock` of a lever does not notify the neighbors of its support block (the game does when it is flipped): in an automatic test you then have to "touch" a block next to each component (change it and change it back) for the circuit to react. Verified: without that touch the doors did not open; with it, they did (Atlantis).
- A pressure plate next to a dispenser fires it without any more wiring, and so does a plate on top of an upward-facing dispenser. Bubble columns must be made explicit in the template (`bubble_column[drag=...]` over soul sand or magma). Audited and generated; not fired in game (Atlantis).
- Two structures from different sets can spawn one inside the other: a vanilla ocean monument appeared inside Atlantis. Rejecting in `ChunkGenerator.tryGenerateStructure` (and in `StructureCheck.canCreateStructure`) the foreign structures whose start falls in the zone prevents it. Verified on a dedicated server by counting elder guardians (Atlantis).
- In 26.3 `spawn_overrides`, each entry takes `count` with an integer provider (`{"type": "minecraft:uniform", "min_inclusive": 2, "max_inclusive": 4}`), not `minCount`/`maxCount`: with the old format the game rejects the whole pack. Verified on a dedicated server (Atlantis).
- Locked chest: `lock` on the block with an item predicate (`{items: ..., predicates: {"minecraft:custom_data": {...}}}`) and the key as an item with that `custom_data` (table with `set_components`). A mob with `DeathLootTable` drops the table when it dies. Verified by reading the data and killing the mob on a dedicated server; not opened with a player (Atlantis).
- A custom structure type can create `PoolElementStructurePiece` directly (with `StructurePoolElement.single(id, LiquidSettings)`): it places templates at fixed positions without a jigsaw or a new piece type. Generating about 2,300 chunks of Atlantis (731,000 template blocks) took 56 s. Verified on a dedicated server.
- To read the 26.3 code: `./gradlew genSources` leaves the sources in `.gradle/loom-cache/minecraftMaven/.../*-sources.jar`.

- `StructureCheck.canCreateStructure` (what `/locate` and maps use) calls `Structure.findValidGenerationPoint`, which for jigsaws only computes the start piece and a height: the assembly is lazy (inside the `GenerationStub`) and the biome is filtered before. That is why asking "would this structure appear here?" from another generation thread is cheap and exact; `StructureCheck` itself is not thread-safe (`HashMap`), so it cannot be used from generation. Verified in the decompiled 26.3 code.
- Separation between kinds without saved data: a "highest rank wins" discard is only consistent if it counts only the neighbors that *survive* (recursion by increasing rank); otherwise a chain A < B < C loses two. Walking the neighbors from highest to lowest rank with per-query memoization cuts the recursion off right away (unsorted, with 1,000-block grids and N = 3,000 the cost exploded). Verified with `UniqueSeparationTest`.
- JUnit tests with game classes need `SharedConstants.tryDetectVersion()` and `Bootstrap.bootStrap()` before touching registries (otherwise "Not bootstrapped"). Verified with `./gradlew test`.
- Fabric API 0.166.2+26.3 conventional biome tags (`fabric-convention-tags-v2` 4.10.5, `data/c/tags/worldgen/biome/`): several are wider than they look in vanilla. `#c:is_forest` = `#minecraft:is_forest`, which includes dark forest, pale garden **and grove**; `#c:is_taiga` includes snowy taiga; `#c:is_savanna` windswept savanna; `#c:is_jungle` bamboo jungle; `#c:is_beach` snowy beach; `#c:is_mountain/slope` meadow, grove, snowy slopes and cherry grove; `#c:is_mountain/peak` the three peaks. Narrow and useful: `is_plains` (plains and sunflower plains), `is_birch_forest`, `is_flower_forest`, `is_dark_forest`, `is_snowy_plains`, `is_desert`, `is_swamp`, `is_stony_shores`; `#c:is_ocean` = `#minecraft:is_ocean`. Terralith puts its biomes into the `#c:` tags through its own tags (`#terralith:reference/...`). Verified by reading the jar and resolving against the mcmeta 26.3 summary.
- In 26.3 advancements are a registry (`Registries.ADVANCEMENT`): a validation problem shows up as "Found validation problems in advancement <id>" and there is no "Loaded N advancements" line. The entity predicate is a map of sub-predicates (`minecraft:entity_type`, `minecraft:location`, `minecraft:nbt`...; without a namespace also works) and `minecraft:entity_tags` exists (`any_of`/`all_of`/`none_of` over the Tags, without serializing the entity). `player_generates_container_loot` uses `loot_tables` (plural) and triggers in `RandomizableContainer.unpackLootTable` only if a player opens it. Without players, `/advancement grant @a only <id>` answers "No player was found" before looking at the id: to check that they load, the mod counts them in the log. Verified in the decompiled 26.3 code and in misode/mcmeta 26.3-data; the loading (63 advancements) and that the guardians' Tags remain in the world after `/place structure`, in the smoke test.
- `/locate` (`ChunkGenerator.findNearestMapStructure`) **can generate chunks**: when `StructureCheck.checkStart` returns `CHUNK_LOAD_NEEDED` (positive prediction in an ungenerated chunk) it calls `level.getChunk(..., STRUCTURE_STARTS)` to confirm it. To search without generating anything, it is enough to stay in `StructureManager.checkStructurePresence`: `START_PRESENT` = generated, `CHUNK_LOAD_NEEDED` = predicted, `START_NOT_PRESENT` = no (also if the chunk already exists without it, e.g. explored before the mod). Also, `/locate` returns the first one it finds in the first ring of cells that has any, not the closest in that ring. Verified in the 26.3 code and with `/heraldia info cerca` against `/locate` in the smoke test (from 6000, 0 `/locate` gave a castle 1,794 blocks away and there was another at 758).
- Predicting structures on the server thread is expensive: with `checkStructurePresence` for the 72 villages in each cell, `/heraldia info cerca` took 415 ms with radius 3,000, 2,065 ms with 6,000 and 3,233 ms with 10,000 ("Can't keep up!"). `findValidGenerationPoint` (with its own `Climate.Sampler`), `UniqueSeparation`, `VillageRules`, `isStructureChunk` and the saved-chunk scanner (`ServerChunkCache.chunkScanner().scanChunk` with `CollectFields`, the one `StructureCheck` uses) are thread-safe: everything runs in `Util.backgroundExecutor()` and on the server thread only the already loaded chunks are looked at (`getChunkNow`, which returns null outside the server thread). Result: 0 ms on the server thread. Measured in the smoke test.
- `ChunkGenerator.getNearestGeneratedStructure` (the `random_spread` one in `/locate`) walks ring r of cells (i and j from −r to r, only the border) and **returns the first** that appears in that order, not the closest in the ring: that is why `/locate #heraldia:minas` from (8000, −8000) gives a large one 6,900 blocks away while there is a small one at 4,200. Each cell goes through `getStructureGeneratingAt` on the server thread. Verified in the 26.3 bytecode (T36).
- In 26.3 the `OCEAN_FLOOR_WG` height (and `MOTION_BLOCKING`) looks at the block tag `minecraft:blocks_motion_in_heightmap` (data, not code): in JUnit, without loading the vanilla tags, `getBaseHeight` always gives the bottom of the world (−64). They are loaded with `TagLoader.loadTagsForExistingRegistries(new MultiPackResourceManager(PackType.SERVER_DATA, List.of(ServerPacksSource.createVanillaPackSource().fullResources())), RegistryAccess.fromRegistryOfRegistries(BuiltInRegistries.REGISTRY)).forEach(Registry.PendingTags::apply)`, and then `new NoiseBasedChunkGenerator(MultiNoiseBiomeSource, settings)` gives the real terrain without a server. A column costs 0.3-0.7 ms. Verified in `MinasDeterminismoTest` (T36).
- The `Climate.Sampler` of `StructureCheck` is created with `SamplerContext.builder().enableCaches()`: it caches and is not meant for several threads. To look at biomes or create a `Structure.GenerationContext` from another thread, use your own with `randomState.createClimateSampler(SamplerContext.EMPTY_UNCACHED)` (same result). Verified in the 26.3 bytecode (T36).
- The prediction of `StructureCheck.checkStart` (the one `/locate` and maps use before loading the chunk) does not look at a placement's exclusion zone (`exclusion_zone`, the one of Heraldia villages against vanilla ones): with the test seed, 4 of the 5 "predicted" villages near 0,0 did not appear when generated. `StructurePlacement.isStructureChunk(state, x, z)` does include it (plus `applyAdditionalChunkRestrictions`). Verified with `/heraldia info cerca` before and after `/locate` generated those chunks.
- A `BlockEntity` keeps the components it does not understand (`components` in its NBT, e.g. `minecraft:custom_data`): they are read when the template is placed (`loadWithComponents`), saved with the chunk, and `components()`/`setComponents` return and change them. It is useful for marking a specific block and storing data in it without mixins. When a chest is broken in survival its table only copies `custom_name`, so that data does not travel with the item. Verified in the 26.3 code and with `data get block` on the Atlantis premium chest in the smoke test.
- Item components (`Item.components()`) are bound when the server data loads (`ReloadableServerResources`): in JUnit, `new ItemStack(...)` fails with "Components not bound yet" until you call `item.builtInRegistryHolder().bindComponents(DataComponents.COMMON_ITEM_COMPONENTS)`. Verified with `CofrePorJugadorTest`.
- Command replies containing "not loaded", "error", "Unknown"... cut the smoke test's wait short (`ERROR_PATTERN` in `server_smoke.py`): success texts must not contain them (in `/heraldia info` it says "not installed" and "unloaded"). Verified when writing the `/heraldia info` test.

- Simulating a player in server tests: Carpet (26.3+v260915, from Modrinth) creates a fake player from the console with `/player <name> spawn at x y z`; `damage <mob> 2000 minecraft:player_attack by <player>` counts as a kill by a player (`killed_by_player` and its `player_killed_entity` are met), and `inventory_changed` advancements are granted when it picks up items. From the console alone, `/kill` and `/loot ... kill` have no player: `killed_by_player` always fails. Verified on a dedicated server (`tools/smoke/trophies.py`).
- A `DeathLootTable` can point to a `minecraft:entity` table that nests, with `{"type": "minecraft:loot_table", "value": ...}`, the mob's own (`minecraft:entities/<mob>`) or a custom `chest` one, plus a second pool with `"condition": {"type": "minecraft:killed_by_player"}`: the game loads it without warnings and the guardian placed with `/place structure` keeps it. Verified on a dedicated server (smoke test and `trophies.py`).
- Translatable written books (26.3): the pages of `written_book_content` are components (`{"raw": {"translate", "fallback", "with"}}`) and are stored as they are; when the book is opened the server "resolves" it (`ComponentUtils.resolve`), which only replaces selectors, scores and NBT and returns another `translate`, so **the client translates each page into its language** (with the mod installed; without it, the `fallback`). Two variants per language are not needed. The `fallback` works as a format with the `with` arguments (which accept numbers). The title is an untranslated string of at most 32 characters and, if not empty, `ItemStack.getCustomName` returns it as the name: `item_name` is not visible in the inventory, you have to set `custom_name` (without italics). And the item on the ground (`ItemEntity.getName`, the `/tp` message) uses `item_name`, not `custom_name`: set both. A page shows 14 lines of 114 px (`BookViewScreen`); anything beyond is not visible. Verified in the decompiled 26.3 code and with `tools/smoke/story.py` on a dedicated server (name in `en_us` in the `/tp` message, pages with their keys in `data get`); not seen with a client.
- The shield with `minecraft:base_color` is called "Red Shield" (ShieldItem sets the color name) and ignores `item_name`; without `base_color`, the banner layer `minecraft:base` paints the background and the `item_name` is visible. And a component equal to the default one (e.g. `rarity: uncommon` on the recovery compass) does not show in `data get entity`: check it with `execute if items ... [minecraft:rarity="..."]`. The `/tp <item> <player>` message shows the name the player sees. Verified on a dedicated server.
- `JigsawStructure.findGenerationPoint` (public in 26.3) only chooses the start piece and its height: the whole assembly runs in the `Consumer<StructurePiecesBuilder>` of the `GenerationStub`, which only runs when the structure is created (not in `/locate`, maps or `StructureCheck`). A custom type can wrap a jigsaw (`JigsawStructure.CODEC.codec()` as a field) and return another stub whose generator calls `village.getPiecesBuilder()`, adjusts the list (removing or adding `PoolElementStructurePiece`) and passes it to the builder: that way the expensive part (finding the shore) is not paid by `/locate`. Measured on the test server: 1 ms the stub, 128-339 ms the assembly of a village. Verified in the 26.3 bytecode (`javap`) and with `/place` (coastal villages).
- `Beardifier` (26.3, `javap`): only **rigid** pool pieces (and non-pool ones) take part in terrain adjustment; `terrain_matching` ones only contribute their junctions. With `beard_thin` each rigid piece fills up to 12 blocks below its box: a rigid dock over the sea would raise a tongue of land. `terrain_matching` rests each column on `WORLD_SURFACE_WG`, which counts water: row y=1 of the template sits right above the water (y=63 with the sea at 63).
- `getBaseHeight` costs ~0.3-0.5 ms per column and heightmap (it evaluates the noise): 16 columns x 2 maps were 4-15 ms, more than the jigsaw stub. To know whether there is water, `OCEAN_FLOOR_WG` < sea level is enough (half the cost). Measured with `System.nanoTime` on the test server (coastal villages).

- Guardian thorns: `Guardian.hurtServer` returns 2 damage (`thorns`) to the melee attacker if the guardian is not moving (with NoAI it never moves), and the hit knocks the attacker back; a `damage ... by <player>` counts as melee. In a test with a simulated player, wait until it is on the ground and not hurt (`nbt={OnGround:1b,HurtTime:0s}`) before relying on its position. Verified in the 26.3 code and on a dedicated server: the player always ended up at z = -1.4886 and `trophies.py` failed 3 out of 5 times, only in Atlantis; with the wait, 10 out of 10.
- Template mobs go through `finalizeSpawn` (reason `STRUCTURE`, group `null`) when a pool piece places them (`SinglePoolElement` sets `setFinalizeEntities(true)`: generation, `/place structure`, `/place jigsaw`), but **not** with `/place template` (`StructurePlaceSettings` leaves it `false`). The zombies' one (zombie, husk, drowned, zombie villager, zombified piglin) ignores the NBT: it rolls baby 5 % of the time (`getSpawnAsBabyOdds`, and of those 5-10 % on a chicken), sets `CanPickUpLoot` at random and its `populateDefaultEquipmentSlots` changes the main hand (zombie and husk 1 % on normal and 5 % on hard; drowned 10 %: trident or fishing rod, and the trident drowned rides a persistent zombie nautilus half of the time if the biome is not in `more_frequent_drowned_spawns`). `IsBaby:0b` in the NBT does not help. Hoglin and zoglin are babies 20 % of the time, always; the piglin not with `STRUCTURE`; `AgeableMob`s (animals, villagers) with a new group never (the first of the group cannot be a baby). Verified in the decompiled 26.3 code and with `tools/smoke/adult_guardians.py` on a dedicated server: without the fix, 4-16 babies out of every 200 per mob appeared (90 out of 1,800 in total), the odd chicken, 64 and 83 nautiluses out of 200 with the Atlantis sentinels (trident) and 16-17 out of 200 drowned from the lighthouse and the galleon with another weapon.
- Testing on the server the real placement path of a template mob without placing the whole structure: a datapack in `world/datapacks/<name>` written before the first startup is enabled on its own ("Found new data pack file/<name>, loading it automatically"); with a minimal template (stone, a named jigsaw that is removed, and the mob) and its pool, `place jigsaw <pool> <jigsaw name> 1 x y z` places it as a pool piece. A function with 200 `place jigsaw` lines runs instantly (it answers "Running function"; errors inside do not show in the console, you have to count what was placed). 26.3 `pack.mcmeta`: `{"pack": {"description", "min_format": 121, "max_format": 121}}`; the template palette is `{id, properties}` (written by `core.Template`). `time set midnight` answers "Set minecraft:overworld to time marker minecraft:midnight". Verified on a dedicated server.

- Rail switches (26.3, `RailState.place`, read in the bytecode): a normal rail with three neighbors that can connect to it takes the curve according to the signal; without a signal the last of NW, NE, SW, SE that has both neighbors wins, with a signal the last of SE, SW, NE, NW. A north-south T with a branch to the east is SE without a signal and NE with it; an east-west T with a branch to the south, SE and SW. A floor lever next to the switch (not next to another track) is enough to change it with `setblock`. Verified with a real minecart on a dedicated server (`lost_mine/smoke_server.py`).
- Minecarts in a puzzle: an empty minecart brakes a lot (0.96 per tick): a single launch booster does not take it far. What works is an unpowered booster against a wall as the launch (when powered it sends the cart away from the wall), a normal insulating rail behind it (otherwise the powered boosters next to it pass it the signal) and boosters with a redstone block underneath every 5-7 blocks; it climbs a ramp and stops on a detector rail at the end of the track against a block, which stays powered while the cart is on it. The detector rail strongly powers the block underneath (like a plate): an inverting torch on that block opens a piston door. A minecart goes through a 1 x 1 gap where a player does not fit. Verified on a dedicated server (the Lost Mine, three switch combinations).
- Underground structure without a box: recording every excavated cell with its lining and adding two layers of rock around it (BFS by faces) leaves the template shaped like the excavation with structure_void outside: no water or lava gets in (the audit requires every excavated cell to have its 6 neighbors written) and a nearby vanilla cave only sees irregular rock. Linings without natural blocks (`#base_stone_overworld`, dirt; the pools of lush caves also replace gravel, sand and clay) so that no springs, lichen, moss or pools appear inside. Lost Mine: 83,000 blocks written for a 108 x 45 x 82 colony. Placed with `/place` and in natural generation on a dedicated server; the look has not been seen with screenshots.
- Cave biomes: the biome of a `GenerationStub` is checked at its 3D position (`Structure.isValidBiome` with the stub's y), so a custom type can give the center of the cavern as its position and the structure appears in lush or dripstone caves even if the surface is something else. `GridPlacement` accepts `bioma_y` to look for the candidate at that height. With the test seed, `/locate` from 0,0 found the Lost Mine 6,637 blocks away in ~1 s (the nearest cell had the biome but not the terrain: sea or a slope). Verified on a dedicated server.

- Villager trades (26.3, `AbstractVillager.addOffersFromItemListingsWithoutDuplicates`, read in the bytecode): when leveling up, `amount` trades are drawn (2; the level 5 librarian, 3) at random from the tag `#minecraft:<profession>/level_N`; if `merchant_predicate` fails (`getOffer` gives null), that trade is removed and another one is drawn. Trades filtered for other villagers do not subtract anything: with n vanilla ones and one of ours, ours appears with probability 2 / (n + 1) and always if n = 1. The 26.3 counts n are in `trades.VANILLA_LEVEL` and `village_life.py` compares them with the game .jar. Verified on a dedicated server: a level 3 librarian trade (n = 3) appeared in 9 out of 12 Heraldia villagers in the square and in 0 out of 12 without the `heraldia` tag.
- A villager's offers are only drawn in `getOffers()` (when a player touches it or when it levels up): in 26.3 `addAdditionalSaveData` saves the field as it is, so `data get entity` does not generate them ("Found no elements matching Offers"). In a test: a Carpet player, `player <name> look at x y z` (looks from the eyes) and `player <name> use once` (answers nothing in the console: do not wait for a line). `tp <player> ... facing x y z` aims from the feet: the ray passed over the villager. Verified on a dedicated server.
- A template villager with fixed `Offers` (`{Recipes: [{buy, buyB, sell (with components), maxUses, ...}]}`), `NoAI`, `Invulnerable` and a translatable `CustomName` keeps everything when placed in natural generation, including the components of the item it sells (name, color, enchantments). `maxUses: 4` is the default value and does not show up in `data get`. Verified with the job board's constable in a generated village (`village_life.py`).
- Location predicates with `structures` (in `merchant_predicate`, advancements, `predicate=`) only see structures whose start is saved: not those from `/place structure`. To test them, `locate structure #heraldia:aldeas` (answers "The nearest #heraldia:aldeas (heraldia:<id>) is at [x, ~, z]") and `forceload` around it: the village is really generated (about 30 s with radius 80). A mob summoned in a chunk just marked with `forceload` is not seen by `@e` until `execute if loaded x y z` succeeds. Verified on a dedicated server.
- Fixed in `village_variants.py`: one variant can contain almost all of another (with town hall c of `llanuras_castellana` placed, template a matches 94 %), so "only one above 85 %" failed depending on the village's draw; now, if there are several, only those within 0.03 of the best count. It came up when adding the job board piece, which changes the jigsaw draw (the special templates did not change). Verified on a dedicated server: 2 out of 6 villages failed this way; with the fix, all 6 give a single variant.
- `execute` commands that answer nothing in the console (a test waiting for "Test passed|Test failed" hangs for 5 min): with `as`/`at <selector>` the command forks and in one branch the "Test failed" is discarded (only "Test passed" arrives); with nobody in the selector there is not even a branch; and in an `if A if B` chain, if an intermediate condition fails there is no answer either. A command without forking and with a single condition always answers (`execute if entity <selector>`, `execute if block x y z ...` with coordinates): to look at blocks next to a mob, read its `Pos` with `data get entity` and check those coordinates. Verified on a dedicated server. That is how `corsair_island/smoke_server.py` hung on CI: the corsair (with AI) had moved onto a 7/8 slab (y = 57.875), its cell was not air and the chain failed silently; it was fixed by checking that there is no water in its cell and in the one above (one command per block), and likewise in `mina_perdida`.
- `nbtlib` does not support NBT lists with mixed types: in a template's NBT, the `with` arguments of a translatable text all go as components (`{"text": "32"}` instead of 32). Detected when generating the job board book.
- The Fabric launcher leaves the game in `.fabric/server/<version>-server.jar`, which is a "bundler": the vanilla data (trade tags...) are in the nested .jar in `META-INF/versions/`. And two test servers at the same time on the same machine clash on port 25565 ("FAILED TO BIND TO PORT"): locally, one at a time (on CI each test runs on its own machine).
- Islet in the open sea (Corsair's Isle): a single template that goes 18 blocks below sea level with solid rock across its whole footprint and a sand slope around it, `terrain_adaptation: none` and the bottom row extended down to the seabed with `heraldia:acueducto_hasta_el_suelo` (which goes through water); outside, `structure_void`, so the sea stays and there is no crater or cut coast. The slope must start at least one block below the water surface: at the surface (y = -1) it leaves a "dry" step at sea level that the walk steps on and never returns from. Seen on a dedicated server.
- **Prove a region is untouched with `execute if blocks <box> <copy> all`**: `clone` the region into the sky above it (same chunks, so it is loaded) before the test, and after each step the check passes only if every block, state and block entity is the same. Used by `tools/smoke/village_events.py` after each event, a restart and a crash.
- 26.3 has no `ItemTags.SMALL_FLOWERS` or `FLOWERS` constant (the tags exist as data, `data/minecraft/tags/item/small_flowers.json`): make the key with `TagKey.create(Registries.ITEM, Identifier.withDefaultNamespace("small_flowers"))`. Coloured wool, carpets, beds and candles are `ColorCollection`s (`Blocks.WOOL.red()`, `Blocks.CARPET.black()`, `Items.DYED_CANDLE.white()`), like the banners. Verified when compiling.

- **A villager with nowhere to meet drifts away and gives up its bed** (medium structures' inhabitants, verified on seed terrain with `tools/smoke/medium_structures.py --stay`): without a reachable bell (the `meeting_point` POI), a villager's idle hours are random strolls from wherever it stands, so it drifts 20-35 blocks and more; in rough terrain (dark forest) it got lost, failed to path back for too long and `SetWalkTargetFromBlockMemory` (26.3) made it **release its bed and its workstation**. A bell on the ground, reachable, within a few blocks of the beds, is the vanilla leash: they idle around it. Before: 13-16 of 17 kept their bed and some were found far away after three days; after: 17 of 17, and 7 of 7 home after three days.
- **A one-block step against a fence is a way in, not out**: a villager hops onto a composter (or a barrel, a hay bale) and from it over the fence (its top is only half a block higher); villagers open doors but **not fence gates**, so a fenced garden with its gate shut traps it, and from there it cannot reach its bed. The hermitage's composter was against its garden fence; `mediums/_inhabitants._fence_traps` now finds it (it walks the template as a villager: without ladders and with closed gates as fences).
- Testing villagers over several days with `/tick sprint`: (1) forceload a wide area (±80 blocks) and **wait for it to load** (`execute if loaded`) before sprinting: with the clock racing while chunks still load, their paths fail and they give up their bed and workstation; in a smaller area they stop ticking at its edge, which looks like "wandered off"; (2) sprint in steps (6,000 ticks): right after a single 72,000-tick sprint the hermit read as having an empty brain (no bed, workstation or bell), yet after a restart it had them all, and in steps it never happened; (3) **do not jump the clock with `/time set` while they sleep** (it wakes them abruptly): run it with the sprint instead. In 26.3 `/time set` answers "Set minecraft:overworld to N tick(s)".
- **Telling a client with the mod from one without it** (choice windows, read in Fabric API 0.166.2 and checked on the test server): `ServerPlayNetworking.canSend(player, type)` is true only if the client registered a receiver for that channel (Fabric's channel registration, sent when it joins). A vanilla client and a **Carpet bot** register none, so both get the container fallback; a Fabric `FakePlayer` (automation) cannot see a window at all. Put the protocol number in the channel id (`heraldia:choice_v1`): a client of another version simply lacks the channel, and no payload of another shape is ever decoded.
- **A Carpet bot cannot click a container slot nor send a custom payload.** To test a container menu as a vanilla client uses it, build a `ServerboundContainerClickPacket` and pass it to `player.connection.handleContainerClick` from an operator command (`/heraldia choice click`): it is the same path as a real click (container id, `stillValid`, slot index, the client's predicted slots and the resync). `execute at <player> if entity ...` hangs a test when it fails (it forks: see `silent_reason`); use `execute positioned x y z if entity ...`.
- **A container menu whose items must never move** (verified with every click kind on the test server, inventory compared before and after): override `clicked` and never call `super` (the vanilla `doClick` handles pickup, quick move, swap with the number keys and the offhand, clone, throw, drag and pick-all); return `ItemStack.EMPTY` from `quickMoveStack`, false from `canTakeItemForPickAll` and `canDragTo`. The click handler then resends whatever the client predicted wrongly. Do the effect of a pick **after** the click packet (`server.schedule(server.wrapRunnable(...))`; `server.execute(...)` on the server thread runs at once): opening or closing a window inside `clicked` leaves the handler writing the old packet's slots into the new menu.
- 26.3 names that changed (read in the sources): `ClickType` is `ContainerInput`; `ChatFormatting` has no colour any more (keep your own 0xRRGGBB); the coloured items are a `ColorCollection` (`Items.STAINED_GLASS_PANE.lime()`); a screen draws in `extractRenderState`/`extractBackground` with a `GuiGraphicsExtractor`, is set with `minecraft.gui.setScreen` and read with `minecraft.gui.screen()`; key events carry SDL-style codes (`InputConstants.KEY_1` is 30). `Screen.isPauseScreen()` is **true** by default (it pauses the single-player world): a chest-like screen returns false, and `isInGameUi()` true for the dimmed world behind it instead of the menu blur.

- **A bed across a chunk border is lost when a template is placed chunk by chunk** (`StructureTemplate.placeInWorld` with a bounding box per chunk, as `herald/Building` and `arena/Works` do): placing one chunk updates the shapes at the edge of what was placed against what lies beyond it (air yet), so the half of the bed in this chunk is removed, and then the other half when its chunk comes. Which beds are lost depends only on where the template falls on the chunk grid. Seen on seed terrain: the Herald's House workshop's two beds were simply missing (`/data get block` found no bed), so its two residents never had one. Fix: once all chunks are placed, set every bed of the template again with no shape updates (`Building.beds`, `filterBlocks` per `BedBlock`). Any other block that spans two blocks horizontally would need the same.
- **A spare bed is a resident's bed lost**: a free bed lets villagers breed, and the child claims the nearest free bed, which may be the one a resident was walking to. The Herald's House now has exactly one bed per resident.
- **Villagers pick the closest bell in a straight line, then idle around it**; what matters for keeping a bed is the *walk* from that bell to the bed, not the straight distance. On seed terrain two librarians took a neighbourhood bell 25 blocks away in a straight line but 45-56 blocks' walk from their bedroom (the library's door faces the other way) and gave their beds up at night; a cleric 66 blocks' walk from its bell kept its, so the limit is not sharp, but every resident that lost a bed was far from it. The Herald's House check (`resident_errors`) measures walks on the villager's walk graph: bed at most 16 blocks' walk from the workstation, bell at most 24 from both.
- **A villager that climbs onto a town wall walk may not find its way down**: a smith went up a corner tower's stair and was found on the wall walk, without its bed or workstation. A fence gate at the tower's foot (villagers open doors, not gates) keeps them down and lets players up.
- **A door that opens onto a bed's foot is not a way in for a villager**, although `lint.walk` walks over the bed (top 0.56): the library's bedroom was reached only across a bed and its beds were never claimed from outside, while a librarian put inside claimed one at once.
- **Sea water a template does not clear stays as still water forever, even inside a dry room**: water placed by world generation (the ocean, Atlantis's base piece) has no fluid tick, so a cell the template leaves unwritten keeps it, and with air all around it does not flow, not after 200 ticks with random ticks on: a 1 × 3 column of water standing in the middle of a dry room. Verified on a dedicated server by removing three 1 × 3 columns of air from Atlantis's tiles (`tools/smoke/aquatic_dry.py` catches the 9 cells). Below Atlantis's pavement the same hole keeps the base piece's stone instead.
- **The third time still water without a tick bit us: ground cut away round a pond** (the owner's spawn, Nov 2026, after the structures' rooms of F3): the grounds' plan left water columns as they were and the shore rule held only where the cut and fill caps allowed it (the columns "too steep to level" were moved to whatever height left the fewest steps, under the water beside them), the town's margin was blended down round any water, and a pond across the footprint's edge was cut in two by the template. Water placed by world generation has no fluid tick, so each of those left a wall of still water standing in the air, for good. Worse, placing the template chunk by chunk updates the shapes at its edge (`StructureTemplate.placeInWorld` without a known shape), which gives the water against that edge a tick: a pond across the wall ran into the town and spread over its streets. Fix (`herald/Shores`): every step that cuts ground (the town's build and the grounds) looks at the still water of every column it shaped once it is done; a pond small enough (4,096 blocks at most, all loaded) drains as it would have run out (everything as high as the lowest place it touched the air), a bigger body gets a bank of ground where it was open, and in the town's footprint no water but the template's own stays. Only source blocks count: flowing water has, or had, its tick. Draining was chosen over banking where it fits because a bank is a cliff of dirt against the town's wall, while a drained pond is dry ground the grounds then level; a lake or the sea cannot be drained, so they are banked. Verified on the owner's seed with a pond made across the town's wall (`tools/smoke/herald_steep.py`): 614 blocks of water standing in the air before, 0 after.
- **An audit that counts only steps of more than one block passes a staircase**: the grounds' audit counted pairs of side by side columns more than a block apart and passed (46 such steps on 32,977 columns) the ring the owner found levelled into "rice terraces": dozens of one-block steps one after another all round the wall. The plan's walkable heights (1-Lipschitz, between the caps) follow a cone of slope 1 wherever the caps bind (down from a town on a hill, up to a road's cut), and the smoothed shape keeps every hillside's own slope: both are exactly one-block staircases. What makes ground look levelled is how far apart its steps are, so the audit now also counts **ramps** (`OutskirtsPlan.ramps`: runs of four or more one-block steps the same way along a row or a column, each within two columns of the next) and the plan gathers ground climbing faster than 0.45 blocks a column into terraces with stone retaining walls. On the owner's seed: 9,268 of 28,258 columns' steps in ramps before (33 %), about 600 after (2 %); on the CI seed 14 % before, 1.5 % after. Gentle slopes everywhere were tried first and cannot be done: the roads' cuts, the huts and the natural edge are fixed points with their own slope of 1, so a slope of 1/3 is infeasible across most of a hilly ring whatever the caps. And a test that reads the saved world back from its region files (`herald_steep.py`) measures the result, not the build's own counters.
- **A road's heights worked out block by block, as each chunk asks for them, cannot climb a cliff the caps cannot cut alone**: each height is within a block of the one before and starts wherever the first chunk asked, so it meets a rise late and the columns' clamp (cut or fill at most 10) leaves a step; the order the chunks load in also changes the result (5, 10, 17 and 41 steps on the same site in four runs). `RoadProfile.prepare` works the whole road out at once before it is paved, once every chunk under its axis and edges is loaded: the mean, made 1-Lipschitz, clamped between the caps' own 1-Lipschitz closures (the highest ground across cut at most 10, the lowest filled at most 10), so a climb starts early enough; where even that cannot be done the caps widen a block at a time, up to 24, only as needed. 0 steps on the owner's spawn.
- **A vanilla feature of the next chunk can write into a structure already placed**: features of a chunk write up to one chunk away, and the neighbour may already have its structure (its features step ran first). An amethyst geode (origin at y ≤ 30, crust up to y ≈ 39) left smooth basalt and calcite inside two dry rooms of Atlantis and its air hollow in the open water of a street; glow lichen grows on stone faces inside dry rooms. That is vanilla and it puts no water in, but any check of a structure's water has to tell those hollows apart (`aquatic_dry.py` only counts air spaces that contain air of a template). Seen reading the saved regions of a naturally generated Atlantis.
- **Seagrass and kelp that lose their support become air, not water**: one- and two-cell air pockets in the open water of Atlantis's streets, beside the kelp, after generation. Harmless, but a water check needs a minimum room size (`aquatic_dry.py`: 20 cells). Also, `existing_world.states` expects the section's `block_states` already passed through `existing_world._blueprint` (26.3 wraps the property-less palette entries as `{"": name}`); with the raw nbtlib value every name comes out `None`.

- **A time limit measured with the clock alone cannot say why it was broken**: a step's `nanoTime` counts a collector's pause, a lock and a descheduled thread as much as work. Log the thread's own CPU time beside it (`ThreadMXBean.getCurrentThreadCpuTime`, about a microsecond a call): clock high and CPU low is waiting, both high is work. The first time this was done for the grounds it showed, in one line, that the slow step waited (21 ms, 3 of CPU) and where (the hand-over to the background pool), after a guess that it "did almost nothing, so it must have been the machine" had been written down as likely.
- **Water taken away without block updates leaves its run-off behind for good** (26.3): removing source blocks with `UPDATE_KNOWN_SHAPE` and no neighbour update (what a spread-over-ticks build uses so nothing pops or drops) schedules no fluid tick, so the flowing water that had already left that source is never recomputed: it stays, with no source, until something else updates it. Whoever removes water that way removes its run-off too (`herald/Shores.dry`: a flowing block is fed if a source is reached from it through water going sideways or up; if not, it and everything on that way goes). Found reading the saved regions of `herald_steep.py`: both the passing and the failing runs held a stream from nowhere (193 and 105 blocks); the audit only counted still water, on the written assumption that flowing water "runs on its own".
- **An intermittent test is two states, and the passing one may be the wrong one**: `herald_steep.py` failed 1 run in 9. Comparing the saved worlds of a passing and a failing run, and a third built without the test's pond, showed three different roads; the one the test called good had plank walkways over a hillside. Before stabilising a flaky test, read what each outcome actually built.
- **A shulker needs a full block face to hold on to** (26.3, `Shulker.canStayAt`): placed by a template on a wall, a fence, a slab or a stair it lets go as soon as it loads and teleports to a free spot with a full face within eight blocks (`teleportSomewhere`), below the structure included. Persistent and anchored do not prevent it: it is the mob's own attachment. Verified on a server with 12 placements of each wharf style (`embarcadero_shulker`: 12 of 12 stay on a purpur pillar, 0 of 12 on an end stone brick wall). An intermittent "its entities do not appear" in a server test was this, one time in four: a test that fails now and then with a mob "missing" is first a question about the mob, not about the test.
- `StructureTemplate.placeInWorld` **keeps the water that was already in a cell**: `StructurePlaceSettings` starts at `LiquidSettings.APPLY_WATERLOGGING`, so for every cell it reads the fluid there, sets the template's block, and, if that block is a `LiquidBlockContainer` (a wall, a stair, a slab, a fence, a lantern, a trapdoor), puts the water back inside it (`waterlogged=true`) whatever the template says; the blocks whose own water was not a source are then waterlogged again from any source beside them, so it carries along the piece's edge. A build that puts a piece inside a pond therefore ends up with its own walls full of water. And not quietly: `SimpleWaterloggedBlock.placeLiquid` sets the block with `setBlockAndUpdate` (neighbour updates and all, which a build spread over ticks takes care never to do) and calls `scheduleTick` for the fluid, so it pours there and then, while the build is still running. `setLiquidSettings(LiquidSettings.IGNORE_WATERLOGGING)` turns that pass off and changes nothing else: the template's own water blocks are set unconditionally, before any of it. Verified in the compiled 26.3 `StructureTemplate` (both lists are only filled when `shouldApplyWaterlogging()`) and on a dedicated server: the Herald's House over a pond left 54 blocks of its wall waterlogged (30 `stone_brick_wall`, 14 `stone_brick_stairs`, 8 `stone_brick_slab`, 2 `lantern`), 0 with the setting; 3 runs each (`tools/smoke/herald_steep.py`).

## Structure design
- Very large structures: building the whole plan in a voxel map and cutting it into tiles aligned with the structure starts makes it possible to audit watertightness and reachability at once; the generic per-template audit would give false warnings at the tile edges (it is skipped with `sin_auditoria_generica`). Verified with the Atlantis audit (it detects a deliberately caused leak).
- A template placed without block updates (as during generation) keeps a circuit "on at rest": a lit redstone torch on its block, sticky pistons extended with `piston_head` and dust at 0. After forcing updates next to them it stays the same, and powering the torch's block retracts both pistons (one next to the torch and another next to the block the torch powers from above). Verified on a dedicated server (castle, `smoke_redstone.py`).
- A tripwire placed already taut (`attached=true` on hooks and wire) fires when a chicken is put in; the dispensers next to the hook get its signal. A stone pressure plate ignites the TNT right under the block it sits on. Verified on a dedicated server.
- 26.3 entity format that loads fine in a template: `equipment` (`mainhand`, `head`...), `drop_chances` as a compound, `attributes` with `id` and `base`, `CustomName` as a compound `{translate, fallback}`. Verified with `data get entity`.
- `/place template` answers "Loaded template ... at x, y, z"; `gamerule doMobSpawning` no longer exists under that name in 26.3 (it gives "Incorrect argument"). Verified on a dedicated server.
- Sticky pistons placed **extended** (with their `piston_head`) in a template and fed by a lit lever stay stable; when the power is removed they retract and pull the block. A secret door "closed while powered" works without depending on updates during generation. Verified with `/place template` on a dedicated server (monastery, `smoke_server.py`).
- `/setblock` of a lever does not update the dust behind its support block: to simulate a player from the console you then have to change the support block (to another and back). `/place template` answers "Loaded template … at x, y, z" and does not apply processors. Verified on a dedicated server.
- In `processor_list` rules, `output_state` is written as a string (`"minecraft:mossy_cobblestone"`), just like in the vanilla 26.3 lists. Verified in misode/mcmeta 26.3-summary.
- Hillsides without Java: a single rigid template that brings its own rock massif (from y = 0 to each terrace, with an irregular slope around it) and explicit air above the terraces, with `terrain_adaptation: none` and a negative `start_height` projected to the surface (the lower terrace sits flush in the center). It works in any rotation: uphill it cuts into the mountain, downhill it shows the crag. Also, the audit's walk covers the whole structure. Applied in the monastery; look in the game not confirmed with screenshots.
- Monster spawners in areas with some light: `SpawnData.custom_spawn_rules` (`block_light_limit` 0-11) prevents the monsters' light-0 rule from silencing them. Not yet verified in game that mobs appear.
- In `rule` processors, `output_state` is a string (`"minecraft:cracked_deepslate_bricks"`) or `{"id": ...}`; the old `{"Name": ...}` format brings down the whole pack ("Unbound values in registry ... template_pool"). Verified with the smoke test.
- The equipment of an entity inside an NBT template (`equipment.mainhand.components` with `minecraft:enchantments`) loses its components when placed, even though the same NBT works with `/summon` (direct format `{"minecraft:sharpness": 2}`, not `{levels: ...}`). For template entities, better without enchantments; health and attributes (`attributes`, `Health`), `CustomName` with `translate`/`fallback` and `PersistenceRequired` are kept. Verified with `data get entity` on a dedicated server.
- A custom structure type (`StructureType` = `() -> MAPCODEC`, registered in `BuiltInRegistries.STRUCTURE_TYPE`) can itself create a `PoolElementStructurePiece` with any rotation from a single-element pool (its processors are kept and the jigsaw is replaced by its `final_state`). `/place structure` passes it a biome predicate that accepts anything: it is detected by testing `plains`. `/locate` also goes through `findGenerationPoint`. Verified when compiling and on a dedicated server.

- In processors (`rule`), `output_state` is a string (`"minecraft:cracked_stone_bricks"`) or `{"id": ...}`; the old `{"Name": ...}` format makes the game reject the whole pool ("Failed to parse either ... No key id"). Verified on a dedicated server (palace).
- Hanging entities (item frames) in a template: without `block_pos` the game discards them when placing ("Block-attached entity at invalid position: null"). Setting `block_pos` is enough (placement recomputes the real position). Verified with `/place template` on a dedicated server.
- Flush piston secret door that works when generated: save the states consistent with the power (sticky pistons `extended=true` with their `piston_head`, redstone torch `lit=true` on the hidden face of the block where the lever goes, lever off). When the lever is turned on, the torch turns off and the pistons pull the door in; a solid block on top of the torch powers the second piston. Item frame + comparator (facing the frame) + iron trapdoor, tripwire with a dispenser above the hook's block, and a plate with dispensers next to it also work. Verified on a dedicated server with `tools/smoke/colosseum_redstone.py`.
- Template mobs go through `finalizeSpawn` when placed: the wither skeleton always gets its stone sword (the one in the NBT is lost), but keeps armor, `drop_chances`, attributes, `Tags` and name. Verified with `data get entity` after `/place structure` on a dedicated server (mansion).
- The server translates translatable `CustomName`s with the mod's `en_us`: the `name=` selector sees the English text, not the `fallback`. To find a structure's mob, better use a tag (`Tags`). Verified on a dedicated server.
- Paintings in templates work with `variant`, `facing` in 2D code (south 0, west 1, north 2, east 3) and `block_pos` as an `IntArray`; they are still hanging after 15 s (16 out of 16). Verified on a dedicated server.
- The map marker type of the woodland mansion is `minecraft:mansion` (not `woodland_mansion`); an invalid name in `MAP` brings down the whole pack when the cartographer trade loads. Verified on a dedicated server (Registry loading errors).
- A redstone circuit saved in its stable state (lit torches, dust with power and shape, powered repeater, sticky pistons extended with their head) generates still and works when operated: a secret bookshelf with pistons pulling to one side (the lower one by quasi-connectivity) and a 4-lever combination with inverters and an OR bus. Verified with `/place template` and by forcing the update next to the torch (`/setblock` of the lever does not update the block that holds it).

- `JigsawPlacement.addPieces` only adds pieces (not even the central one) if `maxDepth > 0`: with 0 it returns an empty stub and `/place` says "Failed to place structure". Verified in the 26.3 code and on a dedicated server (galleon).
- `JigsawPlacement.addPieces` draws the rotation with the first roll of `context.random()`; a custom type can fix the rotation by passing a copy of the `GenerationContext` with a `WorldgenRandom` whose first roll gives the desired rotation. The biome is validated at `stub.position()`, which can be rebuilt (`new GenerationStub(pos, stub.generator())`). Verified with the galleon on a dedicated server (sea/sand orientation checked with `execute if block`).
- `/place structure` passes `b -> true` as the biome predicate: a custom type tells it apart from natural generation by testing a biome that is not on its list (e.g. `the_void`). Verified in the 26.3 code and in the smoke test.
- In `rule` processors, `output_state` is written as a string (`"minecraft:air"`); the `{"Name": ...}` form makes the whole pack fail to load. Verified on a dedicated server.
- The `name=` selector does not find a mob whose `CustomName` is `{"translate", "fallback"}` (on a server); to find it, use `nbt=` or another mark. Verified on a dedicated server.
- Buried structure with a façade on the hillside (citadel): a single template with `terrain_adaptation: none`, `structure_void` outside the rooms and a 2-block skin (carved wall inside, stone outside so it blends with the mountain and admits ores); the Java tries rotations and positions with `getBaseHeight` (flat and dry in front, rock above in 75 % of a grid of ceilings written by the generator). The inner faces must not be natural blocks (`stone`, `deepslate`, `tuff`...) so that springs and lichen do not appear inside. Verified with `/locate` (1.8 s to find a site) and `/place` on a dedicated server; the look on a real hillside has not been seen in game.

- Basements without sinking the surroundings: if the concept calls for something "under" a building, it can go inside a platform or plinth above the terrain (the palace keeps its treasure chamber inside the three-tier platform); the box starts at the plinth and `beard_box` only fills below. Explicit air in the whole volume of the piece prevents a hillside from poking into courtyards and rooms. Verified with the audit and by placing the structure in the smoke test; the look on a hillside has not been checked in game.
- Piston secret doors that work when generated: leave them closed with the pistons extended and the lever on (stable state: nothing waits for an update), without redstone dust. The lever strongly powers its support block and that one the adjacent piston; the piston above another activates the one below by quasi-connectivity. A column in front hides pistons and heads. Verified on a dedicated server (`tools/smoke/palace_redstone.py`: removing the lever opens the door).
- Traps without dust: a tripwire hook strongly powers the wall it rests on, and that block activates an adjacent dispenser; a pressure plate activates the dispensers touching it. Verified on the same test server.
- Stepped roofs: each course rests only by an edge on the one below; filling the roof solid under each course avoids "floating" blocks and allows removing loose tiles as ruin without opening holes. Verified with the palace's face-connection check.
- To place something next to the sea a custom single-piece structure type is enough: pre-check the biome at the candidates (cheap, `ctx.biomeResolver()`), query `OCEAN_FLOOR_WG` and `WORLD_SURFACE_WG` (water = the second higher and the first below sea level), and create the `PoolElementStructurePiece` with the chosen rotation and `move` to center it. `/place structure` passes a biome predicate that accepts everything: that is how it is told apart from normal generation. Verified with `/locate` and `/place` on a dedicated server (lighthouse).
- Redstone that works when generated: leave the circuit in its stable state (levers, torches lit or not, dust power computed) and test on the server by changing the levers with `setblock` and then **replacing the block they are attached to** (`setblock` of a lever does not notify that block, a click does). Verified: the lighthouse doors and trapdoor respond only to the correct combination.
- A cave at sea level does not flood if all its air is above the water row and the channel's water is source blocks placed at sea level. Verified on the server (air in the grotto, water in the channel and outside the mouth).
- Basements without sinking the terrain (ice fortress): put the crypts inside a **solid plinth** that starts at y = 0 of the template; the fortress rises on top and is reached by a flight of steps. `beard_thin` only fills under the base. Verified with `/place structure` in the smoke test.
- Secret doors that work when generated without block updates: save the state **powered at rest and consistent** (lever `powered=true`, dust with its exact power, sticky pistons `extended=true` with their `piston_head` and the block in front). Turning the lever off retracts them. Cross-shaped dust on a block powers the piston it points at and, through the block underneath (weakly powered), the adjacent piston. Verified with `/place template` and `setblock` of the lever on a dedicated server (careful: `/setblock` of the lever does not notify the neighbors of the attached block; the test changes that block right afterwards to emulate real use) (`tools/gen/uniques/ice_fortress/smoke_server.py`).
- Traps like the temple ones: a dispenser next to the block the tripwire hook is attached to, or next to a pressure plate, gets a signal when stepped on. Verified on a dedicated server (a zombie without AI steps on the plate and crosses the wire; the dispensers lose arrows).
- Ice spikes: the feature spawns on `snow_block` at the surface. Do not put snow blocks on exposed tops (or as the output of a processor that might land on a top) in snowy-biome structures. Verified in the 26.3 code (`IceSpikeFeature`); the fortress audit checks it.
- Basements without a crater: with a single template, `start_height: {"absolute": -N}` + `terrain_adaptation: "none"` sinks the piece N blocks (layer N ends up at terrain level) and the terrain around is untouched. For slopes, a terrace with a foundation and a few blocks of air above. Verified in the wizard's tower (`/place structure` in the smoke test).
